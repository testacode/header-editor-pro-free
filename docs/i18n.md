# Internationalization

The popup ships in 7 languages. This is what you need to know to add a string,
add a language, or review a translation.

There are **two independent translation systems** in this repo, and they do not
share strings: the extension (`src/_locales/`, everything below) and the GitHub
Pages site ([`site/locales/`](#landing-page-github-pages), at the end). Same 7
languages, different catalogs, different key formats.

| `es`    | Español            | LLM           | **no**                       |

Every unreviewed file carries a `zzMachineTranslated` key. To list what still
needs checking:

```bash
grep -l zzMachineTranslated src/_locales/*/messages.json
```

A reviewer deletes that key when they are done — that is the whole bookkeeping.

Users can report a bad string through the
[translation issue template](../.github/ISSUE_TEMPLATE/translation.yml), linked
from the README. Until a native speaker reviews a locale, that feedback is the
main signal we have — treat it as high-value.

## Where things live

- `src/_locales/<locale>/messages.json` — the catalogs, in Chrome's format.
  Single source of truth: the popup imports them **and** the manifest resolves
  `__MSG_appName__` and `__MSG_appDesc__` from them, which is how both stores
  get a localized listing title and summary.
- `src/popup/i18n.js` — `t()`, `applyI18n()`, `LocalizedError`, the locale
  resolution and the stored preference.
- `src/__tests__/locales.test.js` — the guard. Run `npm test` after touching a
  catalog.

## Why not chrome.i18n.getMessage

`chrome.i18n` always resolves against the browser's UI language and offers no
way to ask for another one. The extension has a language selector, so the popup
does its own lookup over statically imported catalogs. `chrome.i18n` is still
used for `getUILanguage()` (the "Auto" default) and by Chrome itself for the
manifest's description.

A consequence worth knowing: the name and description shown in
`chrome://extensions` and in the stores follow the **browser's** language, not
the selector. There is no API to change that.

### The two store-facing keys

`appName` and `appDesc` are the only keys no code references — the manifest
resolves them, so `locales.test.js` allows them in its unused-key assertion.
They carry hard limits that a store enforces at review time, not at build time:

| Key | Limit | Enforced by |
| --- | --- | --- |
| `appName` | 75 chars | Chrome (per locale) |
| `appName` | 50 chars | AMO — truncates instead of rejecting |
| `appDesc` | 132 chars | Chrome (per locale) |

Spanish and Russian sit within a handful of characters of the `appDesc` ceiling.
The tests assert all three limits across the 7 catalogs, so a translation that
overflows fails locally instead of coming back as a store rejection days later.

The name is localized on purpose (since 2.6.1). AMO ranks the `name` field far
above every other one and indexes it once per translation, so a translated name
is the largest search lever available there. `appTitle` is a different key: it
is the popup's `<title>`, deliberately kept short, and unrelated to the stores.

## Adding a string

1. Add the key to `src/_locales/en/messages.json`. Include a `description` when
   the string has a `$1`, quotes another UI label, or is otherwise ambiguous —
   `description` lives in `en` only.
2. Use it: `t('yourKey')` in JS, or `data-i18n="yourKey"` in HTML
   (`data-i18n-title`, `data-i18n-placeholder`, `data-i18n-value` for
   attributes).
3. **Add the key to all 6 other catalogs.** `locales.test.js` fails otherwise.
4. `npm run format && npm test`.

### Naming

`<area><Thing>` in camelCase: `toolbarPause`, `filtersDomainsIgnored`,
`errInvalidJsonFormat`. Chrome requires `[A-Za-z0-9_]` and treats names
**case-insensitively**, so `appName` and `appname` would collide. `@@`-prefixed
names are reserved.

The `err` prefix marks messages that can land in an error slot — those are the
ones that must be thrown as `LocalizedError`, never as a plain `Error`.

### Interpolation

Chrome's format, not template literals: `$1` … `$9`.

```js
t('infoVersion', '2.5.3'); // "Version 2.5.3"
```

A literal `$` is written `$$`. Substitutions are clamped to 1000 characters —
`chrome.i18n` returns an empty string above 1024, and blank UI is much harder to
debug than truncated text.

**There is no plural support and none is coming.** Russian alone needs three
forms. Phrase around it instead: `Valid JSON — profiles: 3`, not
`Valid JSON (3 profiles)`.

## Errors that reach the UI

`throw new LocalizedError('errKey', ...subs)` — never a plain `Error` — and
render with `describeError(err)`. It translates ours and passes anything else
through, which matters because the same catch blocks also see `JSON.parse`
`SyntaxError`s carrying V8 text we cannot localize.

## Reviewing a translation

- The `$1` count must match English exactly. `locales.test.js` enforces this.
- Keep it short. The popup is 600px wide; the color-picker tabs sit two per row
  and `.filter-label` has `min-width: 80px`.
- Do not translate: `Header Editor Pro` (brand), `GitHub`, `CharlyBrown`, the
  example domains in `filtersDomainsPlaceholder`, or `exportFilenameFallback`
  (it becomes a filename — lowercase ASCII, no spaces).
- `errProfileListImport` and `errCannotReplaceMultiple` quote the
  `modalModeNew` label verbatim. Keep the three consistent.
- Watch for over-specific terms. `sectionAddHeader` sits under **both** the
  request and the response section, so it must stay generic — this is exactly
  what "添加请求头" got wrong on the first pass.

## Verifying

```bash
npm test                       # catalog parity, $N counts, key usage
python3 plans/verify-i18n.py   # all 7 locales in a real Chrome
```

The second one is the useful one for translations: it forces each locale, then
flags any element whose text overflows its box, any `data-i18n` that rendered
empty, and any leftover `⟦key⟧` marker. It writes screenshots to
`/tmp/hep-i18n-<locale>-{main,modal}.png` for a human to look at.

## Adding a language

1. `src/_locales/<locale>/messages.json` — copy `en`, translate, keep
   `zzMachineTranslated` if it is machine-translated.
2. Import it in `src/popup/i18n.js` and add an entry to `SUPPORTED_LOCALES`
   (code, `nativeName` — the language's own name — and a flag).
3. Add the locale to `LOCALES` in `plans/verify-i18n.py`.
4. `npm test && python3 plans/verify-i18n.py`.

Use underscores (`zh_CN`, never `zh-CN`), and prefer a bare language code (`es`)
over a regional one so Chrome matches `es-AR`, `es-MX` and `es-419` down to it.

Note that `zh_TW` does **not** match a `zh-HK` browser; that would need its own
directory.

## Landing page (GitHub Pages)

The site at `testacode.github.io/header-editor-pro-free` is pre-rendered: one
static page per language, so every translation gets indexed on its own URL.

### Where things live

- `site/templates/<page>.html` — the three pages (`index`, `privacy`, `404`) with
  `{{key}}` placeholders.
- `site/locales/<locale>.json` — flat catalogs, dotted keys (`hero.tagline`).
  **Nothing to do with `src/_locales/`** — different format, different strings.
- `scripts/build-site.js` — the generator. `npm run build:site`.
- `site/__tests__/site-locales.test.js` — the guard: every key used must exist in
  all 7 catalogs, with no unused and no empty ones.

### ⚠️ The generated HTML is not source

`index.html`, `privacy.html`, `404.html` and the `es/ ja/ ko/ ru/ zh-CN/ zh-TW/`
directories are **build output, committed** so GitHub Pages can serve them. Edit
`site/templates/` and rebuild; a hand edit at the root is silently overwritten by
the next `npm run build:site`.

`sitemap.xml` is generated too, with `hreflang` alternates for all 14 indexable
URLs.

### Locale codes differ from the extension

The site uses **hyphens** (`zh-CN`), because they land in URLs and in the
`hreflang` attribute, where the BCP 47 form is what crawlers expect. The
extension uses **underscores** (`zh_CN`), because that is what Chrome's
`_locales` format requires. Same language, two spellings — don't unify them.

### Adding a string

1. Add the key to `site/locales/en.json` and use `{{your.key}}` in a template.
2. Add it to the other 6 catalogs. The test fails otherwise, and so does the
   build: a missing key is reported and exits non-zero.
3. `npm run build:site && npm test`, then commit the regenerated HTML.

### Tone

Each language gets its own register rather than a literal translation, and the
donation copy leans on it most: English keeps a light wink, Spanish is openly
rioplatense (`doname un cafecito, guachín`), the CJK locales stay polite and
plain. Translate the intent, not the words.

### Gotcha: GitHub Pages serves a single 404

Pages only ever serves `/404.html` from the root — the per-locale copies exist
for direct links, but a missing path at any depth gets the English one. That is
why the 404 template uses **absolute** URLs: relative ones would resolve against
the bogus path that triggered it.
